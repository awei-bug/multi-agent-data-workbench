# Production 审批部署说明

## 目标

在 Staging 自动部署之上，增加 **Production 受保护发布**：

1. 仅允许版本标签（`vX.Y.Z`）进入 production
2. 通过 GitHub Environment `production` 做人工审批
3. 审批通过后 SSH 部署到生产主机并做健康检查

## 发布链路

```text
git tag v1.2.0
   │
   ▼
CD: build-and-push → GHCR
   │
   ├─ deploy-staging (自动，environment: staging)
   │
   └─ deploy-production (environment: production，需审批)
         └─ SSH → production host → compose pull/up → health check
```

## 一次性准备

### 1) 创建 GitHub Environments

仓库 Settings → Environments：

1. 创建 `staging`
2. 创建 `production`
3. 在 `production` 中开启：
   - **Required reviewers**（至少 1 名审批人）
   - 可选：Deployment branches = 仅 tags / 指定规则

### 2) 配置 Production Secrets

| Secret | 说明 |
|---|---|
| `PRODUCTION_HOST` | 生产主机 |
| `PRODUCTION_USER` | SSH 用户 |
| `PRODUCTION_SSH_KEY` | 私钥 PEM |
| `PRODUCTION_SSH_PORT` | 可选，默认 22 |
| `PRODUCTION_DEPLOY_PATH` | 可选，默认 `/opt/workbench-prod` |
| `PRODUCTION_ENV_FILE` | 可选，默认 `/opt/workbench-prod/.env` |
| `PRODUCTION_HEALTH_URL` | 可选，默认 `http://127.0.0.1:8787/api/health/ready` |
| `PRODUCTION_REGISTRY_USER` | 可选 |
| `PRODUCTION_REGISTRY_TOKEN` | 可选 |

> 未配置 `PRODUCTION_HOST` 时，production 部署自动跳过。

### 3) 生产服务器准备

```bash
sudo mkdir -p /opt/workbench-prod
sudo chown "$USER":"$USER" /opt/workbench-prod
cp .env.production.example /opt/workbench-prod/.env
# 修改数据库密码、AUTH_SECRET、域名、Sentry 等
```

确保：

- Docker / Compose 可用
- 能拉取 GHCR 镜像
- 部署用户有目录写权限

## CD 触发规则

文件：`.github/workflows/cd.yml`

### Staging
- `v*` 标签：自动部署（若配置了 `STAGING_HOST`）
- 手动 workflow：`deploy_staging=true`

### Production
必须同时满足：

1. 镜像推送成功
2. 配置了 `PRODUCTION_HOST`
3. 版本号是 `v*`（如 `v1.0.0`）
4. 触发方式为：
   - 推送 `v*` 标签，或
   - 手动 workflow 且 `deploy_production=true`
5. GitHub Environment `production` 审批通过

## 推荐发布流程

1. 合并 main，确认 CI 全绿  
2. 打版本标签：

```bash
git tag v1.2.0
git push origin v1.2.0
```

3. CD 自动：
   - 构建并推送镜像
   - 部署 staging
4. 在 GitHub Actions 中审批 **production** deployment  
5. 审批通过后自动部署生产  
6. 验证：

```bash
curl -fsS https://app.example.com/api/health
curl -fsS https://app.example.com/metrics
```

## 手动触发 production

Actions → CD → Run workflow：

- `push_images=true`
- `tag_override=v1.2.0`
- `deploy_staging=true`（可选）
- `deploy_production=true`

然后在 Environment 审批页确认。

## 本机紧急生产发布（不走审批）

仅用于紧急场景，仍建议双人复核：

```bash
export DEPLOY_HOST=prod.example.com
export DEPLOY_USER=deploy
export DEPLOY_SSH_KEY_PATH=~/.ssh/prod_deploy
export DEPLOY_PATH=/opt/workbench-prod
export DEPLOY_ENV_FILE=/opt/workbench-prod/.env
export IMAGE_PREFIX=ghcr.io/<owner>/<repo>
export IMAGE_TAG=v1.2.0
bash tools/ssh-deploy.sh
```

## 回滚

```bash
export DEPLOY_HOST=prod.example.com
export DEPLOY_USER=deploy
export DEPLOY_SSH_KEY_PATH=~/.ssh/prod_deploy
export DEPLOY_PATH=/opt/workbench-prod
export IMAGE_PREFIX=ghcr.io/<owner>/<repo>
export IMAGE_TAG=v1.1.0
bash tools/ssh-deploy.sh
```

## 生产检查清单（发布后）

- [ ] `/api/health` 与 `/api/health/ready` 正常
- [ ] `/metrics` 可访问
- [ ] 登录/JWT 正常
- [ ] 工作流可启动并完成
- [ ] worker 在线
- [ ] Redis 限流 backend=redis
- [ ] Sentry/告警通道有心跳或测试事件
- [ ] 外部连接器（如启用）可测试

## 安全建议

1. production 强制 `WORKSPACE_AUTH_REQUIRED=true`
2. Secrets 与服务器 `.env` 分离管理
3. Environment 审批至少 1 人，关键变更 2 人
4. SSH 仅密钥，限制来源 IP
5. GHCR token 最小权限
6. 发布窗口与回滚版本提前确定

## 当前边界

- 已支持 staging 自动部署 + production 审批部署
- 仍是 VM + docker compose 模型（非 K8s）
- 蓝绿/金丝雀未内置；回滚通过切 `IMAGE_TAG` 完成
